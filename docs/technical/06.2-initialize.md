### 6.2 Initialize

```http
POST /api/v1/axdata/init
```

New transaction request:

```json
{
  "transId": "salesorder",
  "key": null
}
```

Existing transaction request:

```json
{
  "transId": "salesorder",
  "key": {
    "field": "recordid",
    "value": "100501"
  }
}
```

Response:

```json
{
  "status": "success",
  "objectId": "01J...",
  "transId": "salesorder",
  "recordId": 100501,
  "readOnly": false,
  "correlationId": "..."
}
```

The response does not expose an object version. The active route is `POST /api/v1/axdata/init`; the former base-path route is not retained as a compatibility alias.

After create authorization, the real Axpert adapter uses one request-owned operation-scoped Init runtime. It loads one mutable current StructDef, creates one Validate/Parser pair from it, and passes that same Validate instance to existing-record AxGet baseline loading. AxGet projection retains only container/row shape, record IDs, and field presence; values and source IDs stay in the mutable StructDef. After one checked on-load pass, the adapter reads final values from that StructDef and returns an initialization payload. Only then does the handler create the final DataObject. New records skip AxGet. Init does not acquire the Set field-engine's process-wide gate, calculate a definition hash, create a revision snapshot, build a second application StructDef, or hydrate/read back a temporary production DataObject.

The response has no `expiresAt`: Redis is the only active state store, so the active key has no inactivity TTL and remains until an explicit close/removal lifecycle action.
